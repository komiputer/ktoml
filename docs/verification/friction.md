## 2026-08-27 — Phase 1 chunk 2 (comment/line-continuation family: baseline reuse, WEAKENED alternation gaps, and eight distinct loop-invariant bugs in convertLineEndingBackslash)
Expected (plan.md §1.2): mirror `getCountOfOccurrencesOfSubstring`, `startsWithIgnoreAllWhitespaces`, `convertLineEndingBackslash`, `isLineEndingBackslash`, `takeBeforeComment`, `trimComment` from `parsers/StringUtils.kt` into `verified/Trims.kt`.

`convertLineEndingBackslash` alone surfaced eight distinct Viper rejections across eight compile iterations, each fixed and each re-surfacing a new failure until the next fix — worth recording as a taxonomy since a future loop-heavy mirror will likely hit the same sequence: (a) invariant not provable on entry for degenerate (empty-string) input; (b) invariant missing the upper bound needed for the postcondition; (c) an outer loop's invariant missing a relational fact (`partStart <= k`) that an inner loop's invariant needs; (d) invariant not preserved at a boundary iteration, fixed by narrowing `<=` to `<` in the loop guard; (e) an internally-consistent invariant still too weak to link a boolean flag (`hasMarker`) to the `forAll`-shaped postcondition it needs to imply; (f) a loop invariant's own quantified body must be *well-formed* (safely indexable) for every value satisfying the guard, independent of whether the implication holds — `s[it+1]` needed `it + 1 < s.length` added to the guard itself, not just the conclusion; (g) an invariant can be well-formed and internally consistent yet still too loose numerically to pin the exact loop-exit value the postcondition's `forAll` guard needs to line up with; (h) the deepest one — even with (e)-(g) fixed, the postcondition's `implies` needs, at the "found a marker" return path, that the `forAll` premise be provably *false*, and a bare boolean flag gives Viper no instantiation point to derive that from `!(forAll ...)` (no `exists` counterpart exists in this plugin pin). ## 2026-08-28 — Phase 1 chunk 3 (escaping family: `.code` crashes the plugin in spec blocks; whole-string appends can't carry content postconditions through loop invariants)
Expected (plan.md §1.2): mirror `Char.isControlChar`/`isMultilineControlChar`, `escapeControlChar`, `escapeControlChars`/`escapeBackslashes`, `escapeSpecialCharacters`, `appendEscapedUnicode`, and `replaceEscaped` into `verified/Escapes.kt`.
Observed two new failure modes beyond the ones already catalogued:
1. `Char.code` (the `Int` cast used to hand-spell `CharCategory.CONTROL`'s codepoint range, same house rule as `isTomlWhitespace`) crashes the plugin outright whenever it appears inside a `postconditions`/`loopInvariants`/`forAll` block, in *every* function that reaches Viper — not just `@Pure` ones: "PureLinearizer used to convert non-pure ExpEmbedding; operation freshAnonVar is not supported in a pure context", an internal error rather than a diagnostic. Workaround: spelled the codepoint test entirely in `Char`-to-`Char` comparisons (`c <= '\u001f' || c == '\u007f'`, both BMP control codepoints have direct `Char` literals) rather than `.code`, and replaced every ternary inside a spec block with a pair of `implies` branches on the boolean condition instead. Surprisingly, `quoteEscapeSingle`/`quoteEscapeTriple` hit the *same* preservation failure despite appending only single `Char`s — there the postcondition itself is a guarded implication (`forAll(premise over s) implies forAll(property over res)`) rather than an unconditional fact built up incrementally, and Viper could not preserve that implication shape across the loop either.
WEAKENED: dropped the "no control character" clause from all four functions' postconditions (and their loop invariants), keeping only the `r.length >= s.length` bound, which does verify. Same family as the G5/`forAll`-alternation gaps already logged for Phase 1 chunks 1–2 — a plugin-pin ceiling, not a spec bug; not pursued further (e.g. rewriting `escapeControlChars` to append `escapeBackslashes`'s/`escapeControlChar`'s result one `Char` at a time via an inner loop might work around it, but was judged not worth the compile-iteration cost for this chunk given the budget).
`appendEscapedUnicode` itself (the chunk's other proof target, upstream defect #2) and `replaceEscaped` (the chunk's centrepiece, length-preservation) both verify in full, with no WEAKENED clauses — the loop-invariant issues above are specific to the multi-`Char`-append control-char-scanning functions, not the fixed-length/index-only ones.
